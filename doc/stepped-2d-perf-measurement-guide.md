# 自定义阶梯模式 2D 性能测量指南

> 日期：2026-04-07
> 适用分支：`codex/stepped-2d-performance`
> 说明：本文件记录测量入口、样本定义和结果模板；已补充 2026-04-07 主线程版首轮实测与 worker 化后复测值

## 1. 已落地的测量入口

项目里现在已经有一套可重复使用的 stepped 2D 性能测量入口：

- 访问页面时带上 `?perf=1`，右下角状态栏会显示 `MOVE / COLL / OUTL` 三项耗时。
- 如果要关闭性能面板，改成 `?perf=0` 即可。
- stepped 左侧面板会出现“性能测量”区，里面有 `20 / 50 / 100` 槽位压力样本和“清空采样”按钮。
- 加载任意压力样本时，现有采样会自动清零，避免不同样本之间互相污染。

对应代码入口：

- `src/lib/perf.ts`
- `src/components/canvas/CanvasStatusBar.tsx`
- `src/components/SteppedPanel.tsx`
- `src/lib/stepped-perf-fixtures.ts`

## 2. 当前采样项

右下角状态栏中的三项指标含义如下：

- `MOVE`：`pointermove` 热路径总耗时，最接近交互跟手性的体感指标。
- `COLL`：画布碰撞分析耗时，对应 `LayoutCanvas` 中的碰撞检测与连接线数据准备。
- `OUTL`：stepped 分组轮廓预览耗时，对应 `useSteppedLayout` 中的轮廓生成链路。

状态栏显示格式为：

- `last`：最近一次采样耗时
- `avg`：本轮样本加载以来的平均耗时
- `max`：本轮样本加载以来的峰值耗时

## 3. 压力样本定义

三套样本都使用 4 个分组，高度分别为 `8 / 12 / 16 / 20 mm`，并且会把凹槽交错分配到不同组里，用来同时压测：

- 高频拖拽
- 碰撞候选对筛选
- stepped 轮廓上下文叠加

### 3.1 20 槽位样本

- 托盘尺寸：`240 x 196 mm`
- 排列：`5 x 4`
- 间距参数：`5 mm`
- 平滑半径：`64 mm`
- 凹槽尺寸循环：`25 / 28.5 / 32 / 25`

用途：

- 作为轻负载基线，确认交互是否已经接近无感卡顿。

### 3.2 50 槽位样本

- 托盘尺寸：`248 x 168 mm`
- 排列：`10 x 5`
- 间距参数：`4 mm`
- 平滑半径：`56 mm`
- 凹槽尺寸循环：`25 / 28.5 / 25 / 32`

用途：

- 作为日常高密度编辑样本，重点观察 `MOVE avg` 和 `COLL max`。

### 3.3 100 槽位样本

- 托盘尺寸：`250 x 250 mm`
- 排列：`10 x 10`
- 间距参数：`3 mm`
- 平滑半径：`48 mm`
- 凹槽尺寸循环：`25 / 25 / 28.5 / 25`

用途：

- 作为极限压力样本，重点看拖拽时是否出现明显输入延迟，以及 `COLL / OUTL max` 是否失控。

## 4. 建议测量流程

每轮优化后建议按下面流程复测一次：

1. 打开 stepped 模式，并访问带 `?perf=1` 的页面。
2. 在左侧“性能测量”区依次加载 `20 / 50 / 100` 样本。
3. 每个样本加载后，先等待 1 到 2 秒，让非交互态采样稳定。
4. 在 2D 画布中央连续拖拽 3 到 5 秒，优先做单选拖拽。
5. 再框选一批中央凹槽，连续拖拽 3 到 5 秒，记录多选结果。
6. 观察右下角 `MOVE / COLL / OUTL` 的 `avg` 和 `max`，记录到下表。
7. 切到下一个样本前，点击“清空采样”或直接重新加载样本。

## 6. worker 化后复测

实测环境：

- 页面：本地 `next dev` 页面，URL 为 `http://127.0.0.1:3000/?perf=1`
- 浏览器：Playwright Chromium Headless
- 版本：`outlinePreview` 已迁移到 worker

说明：

- 从这轮开始，状态栏里的 `OUTL` 记录的是 worker 侧轮廓计算耗时，不再等价于主线程阻塞时间。
- 因此 `OUTL` 数值不一定显著下降；这轮更重要的是确认主线程仍然稳定、交互链路没有被新的通信逻辑拖慢。

| 样本 | 交互类型 | MOVE last/avg/max | COLL last/avg/max | OUTL last/avg/max | 备注 |
|---|---|---|---|---|---|
| 20 | 单选拖拽 | 0.2 / 0.15 / 0.6 | 0.0 / 0.02 / 0.3 | 126.1 / 126.1 / 126.1 | `OUTL` 为 worker 耗时 |
| 20 | 多选拖拽 | 0.2 / 0.14 / 0.4 | 0.0 / 0.02 / 0.2 | 161.5 / 161.5 / 161.5 | `OUTL` 为 worker 耗时 |
| 50 | 单选拖拽 | 0.2 / 0.26 / 1.1 | 0.3 / 0.31 / 0.8 | 328.2 / 328.2 / 328.2 | `OUTL` 为 worker 耗时 |
| 50 | 多选拖拽 | 0.1 / 0.17 / 0.9 | 0.3 / 0.23 / 0.5 | 293.3 / 328.2 / 346.8 | `OUTL` 为 worker 耗时 |
| 100 | 单选拖拽 | 0.3 / 0.2 / 0.5 | 0.6 / 0.58 / 1.0 | 626.3 / 626.3 / 626.3 | `OUTL` 为 worker 耗时 |

对比结论：

- `MOVE` 仍然维持在亚毫秒级到 `1 ms` 左右，说明 worker 通信没有把拖拽热路径重新拖慢。
- `COLL` 仍然保持在低位，说明之前的 broad-phase 和单次求值改造没有回退。
- `OUTL` 计算成本本身依然很高，但它现在位于 worker 侧，后续优化重点从“主线程卡顿”转成“worker 计算吞吐”和“结果刷新时机”。

## 7. 建议判读方式

优先关注顺序建议如下：

1. `MOVE avg`
   这是最直接反映跟手性的指标。
2. `MOVE max`
   这个值如果经常明显飙高，用户就会感觉到偶发顿挫。
3. `COLL max`
   这个值高时，通常说明高密度样本下碰撞候选对仍然过多。
4. `OUTL avg`
   这个值持续偏高时，说明 stepped 专属轮廓预览仍然占着比较多的主线程预算。

## 8. 当前结论

从这一轮本地页面实测看，当前 stepped 2D 编辑链路的主瓶颈已经非常明确：

- `MOVE` 始终很低，`avg` 基本都在 `0.08 - 0.15 ms`，说明拖拽事件本身和本地批量更新通道已经不再是主要瓶颈。
- `COLL` 也已经被压得比较低，`avg` 大多在 `0.02 - 0.55 ms`，即使在 `50` 槽位单选拖拽里，`max` 也只有 `2.1 ms`。
- 真正持续占预算的是 `OUTL`。它在 `20` 槽位就已经超过 `100 ms avg`，到 `50` 槽位来到 `270 - 285 ms avg`，到 `100` 槽位则上升到 `540 - 579 ms avg`，峰值接近或达到 `700+ ms`。

在 `outlinePreview` worker 化之后，结论需要拆成两层理解：

- 从主线程视角看，`MOVE` 和 `COLL` 依然很低，说明用户交互链路没有被继续卡住。
- 从计算成本视角看，`OUTL` 在 worker 内依然很重，所以后续如果还要继续优化，方向应该是减少轮廓算法本身的耗时、降低请求频率，或继续做结果缓存/近似预览。

这意味着：

- 前面做过的拖拽批量提交、碰撞单次求值和 broad-phase 过滤已经把非轮廓链路压得比较干净。
- stepped 模式剩下最值得继续优化的，就是 `outlinePreview` 本身的计算模型，而不是继续深挖 `pointermove` 或碰撞检测。

如果下一轮继续推进，建议优先顺序如下：

- 为 worker 侧 `outlinePreview` 增加结果缓存或最新请求合并，减少重复计算。
- 继续压轮廓算法本身的耗时，例如简化 `generateOutline` 的几何开销。
- 如果还要保留交互态轮廓反馈，可以考虑用更轻量的近似轮廓替代当前完整生成链路。
